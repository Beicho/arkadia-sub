# Arkadia 后台与自动同步设计

## 目标与边界

本次改造聚焦三个日常运营痛点：用户数量增长后管理页不可用、代理池无法方便复测且挑选范围过窄、付费订阅源需要人工搬运。生产继续维持单个 Next.js 容器与 PostgreSQL，不引入新的队列或外部调度服务。GitHub Actions 负责测试、构建和镜像发布；本轮开发本地不执行构建或测试。

后台视觉延续现有 Arkadia 的紧凑控制台语言，重点提高信息密度、操作反馈和移动端可用性，不做与现有站点割裂的重绘。用户管理用 URL 查询参数保存页码、每页数量、关键词和状态，服务端直接对数据库分页并返回总量。这样页面可分享、刷新不丢筛选条件，也不会再一次读取固定 300 名用户。

## 同步与代理数据流

上游订阅同步由一个服务端编排函数负责。它从后台保存的 URL 拉取内容，限制响应大小和超时，依次尝试纯文本 URI、整段 Base64 以及 Clash YAML 中的代理项；所有识别出的有效节点去重后保留。随后从已测活代理池中挑选最多 60 个：先取最多 30 个原生或家宽候选，再从未选中的全部候选中按实测延迟取最多 30 个；任一组不足时使用另一组回填，同时保留网段与地区多样性约束。

最终节点集合是“订阅全量节点 + 当次 60 个代理”，只创建一个新批次并在事务内切换激活，避免两个定时任务互相覆盖。手动同步与每 4 小时自动同步共用相同函数。后台进程通过现有 instrumentation 启动调度；进程内锁防止本实例重入，数据库 advisory lock 防止多实例并发。自动批次使用上海日期，因此同一天内四小时更新不会让用户重复扣额度。

## 失败处理与安全

同步失败时保留当前激活批次，不创建空批次；后台记录最近结果、时间、节点数和错误摘要。HTTP 请求只接受 `http/https`，设置连接超时、响应体上限、禁止把上游正文写入日志。默认订阅 URL 仅在服务端设置与管理员页面中使用，普通用户接口不返回它。仓库当前为私有，但 URL 仍按敏感配置对待，不在审计明细或错误消息中完整输出。

代理复测支持全池、失败项和未测项等范围；运行期间禁用重复启动并展示进度。导入不再因为缺少原生/家宽标签而丢弃普通高速代理，风险标签仍用于展示与优先级判断。自动同步即使代理池没有 60 个可用项，也会发布完整上游订阅，并把实际附加数量写入状态。

## 验证与交付

代码提交前只进行差异、类型结构和安全规则的静态审阅，不在本地运行测试或构建，以遵守用户要求。推送 `main` 后由现有 GitHub Actions 执行数据库 schema push、Vitest、Next.js build 和 Docker 镜像发布。若 CI 失败，依据远端日志修复后创建新提交，禁止强推或覆盖历史。
